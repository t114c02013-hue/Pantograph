# 團隊分工規則（給在這台電腦上工作的 Claude）

負責人 terry 的要求：善用底下的員工，不要所有事情都自己做。我的主要工作是**分派、整合，以及審查結果是否符合 terry 的要求**。

## 1. 什麼時候分派

- 一段工作裡有**彼此不依賴**的部分，就分給員工（子代理）同時做。例如：
  - Blender 建模腳本
  - Unity 建置腳本
  - 測試
  - 報告與文件
  - 大範圍搜尋（找出所有用到某個 ID 的地方）
- 一定要分派的工作：
  - 每段的 ponytail-review（交給 code-reviewer）
  - 新測試的設計與撰寫（交給 test-engineer）
  - 涵蓋整個專案的搜尋與盤點（交給 Explore）
- 我自己做的只有：
  - 分派
  - 驅動 Unity 編輯器（同一時間只能一個人操作開著的 Unity）
  - 合併
  - 驗收

## 2. 怎麼分派

每次分派都要在任務說明裡寫清楚：

1. 要做什麼，以及完成的標準：要改哪些檔案、要過哪些測試或檢查。
2. 不准動的紅線：
   - 判定規則、門檻值、資料 GUID、asmdef 分層、公開介面、黑板鍵、事件名稱
   - 不刪測試
   - 不刪也不移動 Recordings
3. 範圍：只能改哪些檔案。**兩個員工不可以同時改同一個檔案。**
4. 遵守 ponytail：
   - 動手前先看能不能刪減或重用既有的程式。
   - 刻意的簡化要加 `// shortcut: <上限>, <何時升級>` 註解。
5. 交回的內容：
   - 改了哪些檔案
   - 略過了什麼
   - 和規格不同的地方
   - 未檢查的項目

## 3. 我的審查清單（員工交回後，我一定親自做）

1. 對照負責人與協調轉達的規格逐項打勾。沒做到的退回，或寫進報告。
2. 編譯 0 錯誤，EditMode 測試全綠，而且數量不減少。
3. 重建場景，StationLayoutCheck 全過。
4. 桌面版 25 步從 SI_01 跑到結算。
5. 有畫面變動的，看截圖確認外觀正確。
6. 用 Logs/backup-<段>.zip 比對，確認改動都在這一段的範圍內。
7. 報告與數字由我寫和核對，不直接轉貼員工的說法。

## 4. 試玩人員的意見

1. 和試玩人員討論。問清楚：
   - 在哪一步、哪個站點、做什麼動作時遇到問題
   - 期望的樣子是什麼
   - 如果有截圖或錄影，會出現在 Recordings/<資料夾>/report.html、session.jsonl
2. 把意見整理成需求單，寫在 Docs/試玩回饋/<日期>_<試玩人>.md。每一條要寫：
   - 現象
   - 重現步驟
   - 對應的規格或步驟 ID
   - 建議的改法
   - 會不會動到判定或紅線
   - 優先度
3. 動到判定、門檻、安全規則、流程順序的意見，先請 terry 或鐵道裁定，不自己決定。
4. 其餘的意見依第 1、2 節分派給員工改良。改完照第 3 節驗收，再回覆試玩人員改了什麼、請他們重測哪幾項。

## 5. 不分派的情況

- 一兩個檔案、幾行就能做完的小修正。
- 需要操作開著的 Unity 編輯器的步驟：重新整理、建置、跑測試、Play、截圖。這些由我依序執行。
- 員工的結果一律視為草稿，要經過我審查才算完成。
