# 教學：自己動手做一個功能（設計 → 程式 → 模型）

給 terry 和新夥伴。目標是不靠 Claude，自己把一個需求從零做到 commit。

全程用兩個真的做過的例子當範本：
- **新功能**：VR 左手握把抓工具袋、移到想要的位置（commit 517c1e4）
- **修 bug**：選備品時，外觀好的那條被判選錯（commit 696f3da）

先看過這兩份，再看這份：
- `Docs/專案設計報告_程式.md`：整體架構
- `Docs/程式邏輯_關鍵程式碼.md`：第 12 節講設計概念

路徑都從 `Assets/_Project/` 起算。

---

## 0. 一張圖看完整個流程

```
需求（一句話）
  │ 1. 設計：問清楚、寫成規格、找出會撞到誰
  ▼
規格（一頁以內）
  │ 2. 程式：找位置 → 先寫純函式和測試 → 接進元件 → 數值放資料檔
  ▼
程式＋測試
  │ 3. 模型（需要的話）：Blender 腳本 → FBX → Unity 匯入 → 場景建置程式接上
  ▼
跑測試、重建場景、戴頭盔試
  │ 4. 自己審一次 → commit（不 push）→ 確認後自己 push
  ▼
完成
```

順序很重要：**先設計再寫程式，先寫測試再接畫面**。最常見的浪費，是寫完才發現跟別的功能衝突。

## 1. 設計：把一句話變成規格

### 1-1 先問這七個問題

拿到需求（例：「按左手握把可以抓起工具袋，放到我想要的位置」），先在紙上回答：

| # | 問題 | 工具袋的答案 |
|---|---|---|
| 1 | **誰、在哪裡、按什麼**？ | 學員、VR、左手握把 |
| 2 | **這個按鍵現在已經在做什麼**？ | 左握把＝抓面板把手、手在格子前拿放工具 → **會衝突** |
| 3 | **怎麼分辨這次要做哪一件**？ | 手碰到袋子上緣＝抓袋子；手在格子前（0.12 m）＝拿工具 |
| 4 | **什麼情況要擋**？ | 不能放到地板下、頭頂上、離站點太遠 |
| 5 | **什麼時候回到原狀**？ | 換站點、重設高度、對調左右 |
| 6 | **數值有哪些**？（一律放資料檔） | 離地 0.15、眼高上 0.1、水平 1.2 m、震動 0.5／0.08 s |
| 7 | **桌機、重播、紀錄受不受影響**？ | 桌機不受影響；放開時發事件給紀錄 |

第 2 題最容易漏。查「這個按鍵現在做什麼」的方法：

- 按鍵表：`Data/Definitions/InputBindingTable.cs`（每顆鍵的功能和說明）
- 實際處理：`Modules/XR/XrPlayer.cs` 的 `Execute`，搜尋那個指令名（例 `"PanelGrab"`）

### 1-2 寫成一頁規格

把答案寫成條列，交出去之前自己讀一次。範本：

```
功能：左手抓工具袋
觸發：VR、左手握把、手碰到袋子上緣（腰帶隧道）
行為：抓著跟手移動，只跟水平轉向、保持直立；放開停在那裡
限制：高度 樓層+0.15～樓層+眼高+0.1；水平離站點 ≤1.2 m（PostureDef）
不衝突：手在格子 0.12 m 內仍是拿工具；右手抓不到
重設：換站點／重設高度／對調左右 → 回預設
回饋：靠近變亮、抓住震動（ToolPouchDef.grab*）
不影響：桌機；紀錄寫 PanelMoved
測試：夾限純函式＋原本的左右手拿工具測試要繼續過
```

### 1-3 修 bug 的「設計」：先找證據，不要先猜

bug 也要先設計，只是第一步改成**找證據**。這個專案每一場訓練都有紀錄：

```
Recordings/<日期_時間_學員>/session.jsonl   ← 每行一個事件
```

備品那次的查法（照著做一次）：

1. 找最新一場：`Recordings` 資料夾依時間排序，取最新的。
2. 找出錯的事件：用編輯器搜尋 `ErrorDetected`，看是哪個錯誤 ID、在哪一步、哪個時間。
3. 往前找相關的狀態：搜尋 `spare_shelf`，看三條備品的 `model`、`cracked` 在什麼時候被改過。
4. 找「奇怪的時間點」：發現 238.5 秒時三條備品被改回外側的排列，但那時候在靠關節側。
5. 看那一刻發生什麼：同一秒有 `UiCommandIssued … RestartStep`，原來是按了「重做本步」。
6. 寫下根因（一句話）：「重做本步把黑板還原成舊排列，但元件自己記的欄位沒跟著還原。」

**規則**：根因寫得出一句話，才開始改程式。寫不出來就是還沒找到。

## 2. 程式邏輯：七個步驟

### 步驟 1：找到該改的地方

| 想改的東西 | 去哪裡找 |
|---|---|
| 步驟內容、完成條件、錯誤規則 | `Data/Source/*.json`、`*.csv`（改完跑匯入器，不改程式） |
| 數值（距離、秒數、震動） | `Resources/*.asset`（Unity 裡直接改） |
| VR 按鍵怎麼反應 | `Modules/XR/XrPlayer.cs` |
| 隨身容器（工具袋、腰包） | `Modules/XR/XrCarryContainer.cs` |
| 場景物件（備品架、零件盒） | `Modules/Worksite/*.cs` |
| 零件狀態（螺栓、滑板） | `Modules/Parts/` |
| 場景長什麼樣、物件擺哪 | `Editor/R1/RoofSiteBuilder.cs`（**不要手動改場景**） |

找不到時，用 VS Code 的「在檔案中搜尋」搜：
- 黑板鍵名，例 `spare.good_slot`
- 物件 ID，例 `env.spare_shelf`
- 按鍵指令，例 `PanelGrab`

### 步驟 2：讀懂現在的程式，列出會被影響的地方

改一個函式前，先搜尋**所有呼叫它的地方**。工具袋的例子：

- `PlaceToolBag` 每幀把袋子放回預設位置 → 抓著時要跳過，不然袋子會被拉回去。
- `XrPlayer` 的左握把會從格子拿工具 → 抓袋子那一下要跳過。
- `XrPouchHover` 手經過格子會震動 → 抓著袋子移動時要關掉，不然一直震。

這三個都是「沒有要改它，但不改就會壞」的地方。

### 步驟 3：會出錯的邏輯，先寫成純函式和測試

**純函式**：只看參數、只回傳結果、不碰場景，可以在 EditMode 測試直接呼叫，幾毫秒跑完。

工具袋的「放下夾限」就是這樣寫的（`Modules/XR/XrCarryContainer.cs`）：

```csharp
public static Vector3 ClampBagDrop(Vector3 pos, float floorY, Vector3 anchor, PostureDef p)
{
    pos.y = Mathf.Clamp(pos.y, floorY + p.toolBagMinAboveFloor, floorY + p.standEye + p.toolBagMaxAboveEye);
    var flat = new Vector2(pos.x - anchor.x, pos.z - anchor.z);
    if (flat.magnitude > p.toolBagMaxReach) { flat = flat.normalized * p.toolBagMaxReach; pos.x = anchor.x + flat.x; pos.z = anchor.z + flat.y; }
    return pos;
}
```

測試（`Tests/EditMode/ToolBagTests.cs`）每個邊界各一行：範圍內不動、太低、太高、太遠。

```csharp
Assert.AreEqual(ok, XrCarryContainer.ClampBagDrop(ok, 2.5f, anchor, p), "範圍內不動");
Assert.AreEqual(2.5f + p.toolBagMinAboveFloor, XrCarryContainer.ClampBagDrop(new Vector3(1f, 2.0f, 2f), 2.5f, anchor, p).y, 1e-4f, "不會放到地板下");
```

**修 bug 時順序相反**：先寫一個「現在會失敗」的測試，重現 bug，再改程式讓它通過。

備品的重現測試（`Tests/EditMode/WorksiteTests.cs`）照著紀錄裡的順序寫：

1. 存外側排列。
2. 拍快照。
3. 換成靠關節排列。
4. 還原快照。
5. 檢查型號和裂紋跟著黑板。

這個測試以後就守住這個 bug，不會再犯。

### 步驟 4：接進元件

純函式寫好、測過，再接到 Unity 元件裡。這一層通常很薄。

備品的修正只有兩行：每次黑板變動時，從黑板讀回型號和裂紋（`Modules/Worksite/SpareShelf.cs`）。

```csharp
protected override void Refresh()
{
    (modelCode, cracked) = Current(State, id, modelCode, cracked);   // 黑板是唯一依據
    ...
}
```

這裡有一條專案的根本規則：**狀態只放黑板（SimState）**。這次的 bug 正是因為有一份狀態放在元件欄位裡，「重做本步」只還原黑板，欄位就對不上了。

### 步驟 5：數值放資料檔

不要在程式裡寫 `0.15f`、`1.2f` 這種數字。做法：

1. 在 `Data/Definitions/` 的定義類別加欄位，附 `Tooltip` 說明（例 `PostureDef.cs`）。
2. 在對應的 `.asset` 加上值（例 `Modules/XR/Resources/PostureDef.asset`）。
3. 程式用 `PostureDef.Load()` 讀。

這樣以後在 Unity 的 Inspector 直接改數值，不用改程式。

### 步驟 6：模組之間只用事件和黑板溝通

需要通知別的模組時，**發事件**，不要直接呼叫對方。工具袋放開時發 `PanelMoved`：

```csharp
Sim.Bus?.Publish(new PanelMoved { panelId = "toolbag", standPointId = ..., x = pos.x, y = pos.y, z = pos.z, yaw = ..., time = SimClock.Now });
```

紀錄模組本來就訂閱 `PanelMoved`，所以不用改紀錄的程式就會寫進 `session.jsonl`。

先找有沒有現成的事件可以用（`Core/Events/`），沒有才新增。

### 步驟 7：跑測試

**在 Unity 裡跑**：選單 Window → General → Test Runner，EditMode、PlayMode 各按一次 Run All。

**用指令跑**（不用開 Unity 畫面，但主專案的 Unity 要先關掉；或在 worktree 跑）：

```bash
"/c/Program Files/Unity/Hub/Editor/2022.3.62f3/Editor/Unity.exe" -batchmode -projectPath "C:/Huang Tai Hsiang/collector shoes" -runTests -testPlatform EditMode -testResults Logs/edit.xml -logFile Logs/edit.log
```

PlayMode 把 `EditMode` 換成 `PlayMode` 再跑一次。結果在 `Logs/edit.xml` 開頭的 `total`／`passed`／`failed`。

**規則：測試數只能增加，不能減少；全部要通過。**

失敗時怎麼查（工具袋的真實例子）：

```
BodyItems_Walkthrough_BothHands：「左手拿不到第 7 格」
```

意思是新做的抓取框太靠近第 7 格，左手在第 7 格按握把時抓到的是袋子，不是工具。解法是回到設計的第 3 題：「手在格子 0.12 m 內就不能抓袋子」。

**測試失敗通常代表設計漏了一個情況，不是測試寫錯。**

## 3. 模型：從 Blender 到場景

這個專案的模型大多是 **Python 腳本產生**的，不是手拉的。好處是改尺寸只要改參數、重跑。

### 3-1 流程

```
Tools/Blender/gen_*.py（參數＋造型）
  │ blender -b --factory-startup -P gen_tool_pouch.py -- --out <資料夾>
  ▼
*.fbx（放到 Assets/_Project/Worksite/Models/...）
  │ Unity 自動匯入（GeneratedModelPostprocessor 統一設定）
  ▼
場景建置程式 RoofSiteBuilder 依「節點名稱」找到位置，掛上元件
  │ 選單 PantographSim → Slice → Build Scene
  ▼
場景 SC_CarbonStripSlice（產生的，不手改）
```

### 3-2 節點名稱就是「程式和模型的約定」

程式不認座標，只認**節點名稱**。工具袋模型裡的約定：

| 節點 | 程式怎麼用 |
|---|---|
| `Pocket_05`…`Pocket_13` | 工具袋第 5～13 格（建置時改名 `Pocket_5`），掛 `ToolRackSlot` |
| `Stow_*` | 格子裡放工具模型的位置 |
| `Model_<toolId>` | 格子裡的工具模型（拿起時複製到手上） |
| `Belt_Tunnel` | 袋子上緣，**左手抓袋子的地方**（這次新用到） |
| `BoltBag`、`SocketCase` | 零件袋、套筒盒 |
| 工具的 `Attach_Grip` | 握把中心＝手拿的位置 |

**改模型時絕對不要改這些名字**，否則建置時會報錯，例如「ENV_ToolPouch.fbx 沒有工具袋第 N 格」。要新增功能點，就在 Blender 腳本加一個空物件（`empty("名稱", 位置, 父物件)`），程式再用名字找。

### 3-3 座標約定

腳本裡的尺寸都用 **Unity 座標**寫：+X 右、+Y 上、+Z 前、單位公尺。由腳本的 `U()` 換成 Blender 座標，匯出時再換回來（詳見 `gen_tool_pouch.py` 開頭說明）。

工具原點＝握把中心；腰包原點＝背面中心，+Y 是袋口。

### 3-4 小改動不一定要動模型

工具袋的抓取框**沒有改模型**：程式在執行時讀 `Belt_Tunnel` 的外框大小，自動包一個碰撞框。

先問自己：「用現有的節點算得出來嗎？」算得出來就不要動模型。動模型就要重匯出、重建場景，牽動的檔案很多。

備品的裂紋則是**場景建置程式**做的，原本只在 3 號建，改成三格都建（`Editor/R1/RoofSiteBuilder.cs` 的 `BuildSpareShelf`），所以要**重建場景**。

### 3-5 重建場景

改了 `RoofSiteBuilder` 或模型後：

1. Unity 選單 PantographSim → Slice → Build Scene。
2. 等它跑完，看 Console 有沒有紅字。
3. 場景檔會有很大的變動（幾萬行），這是正常的，一起 commit。

Git LFS 注意：fbx、png 是大檔，用 LFS 存。push 時會自動上傳，不用另外處理。

## 4. 收尾：自己審、commit、push

### 4-1 自己審一次（照這張表）

- [ ] 根因或需求一句話講得出來
- [ ] 所有呼叫者都看過（步驟 2）
- [ ] 狀態都在黑板，沒有藏在元件欄位
- [ ] 數值都在資料檔
- [ ] 有測試；修 bug 有「先失敗後通過」的重現測試
- [ ] 測試數沒有減少，全部通過
- [ ] 沒有改錯誤 ID 的意義、沒有刪錯誤 ID
- [ ] 桌機模式、重播有沒有受影響
- [ ] 沒有手動改場景

### 4-2 commit

只加自己改的檔案，不要 `git add .`（資料夾裡常有 Unity 自己改的換行、材質，跟這次無關）：

```bash
git status
git add Assets/_Project/Modules/XR/XrCarryContainer.cs Assets/_Project/Tests/EditMode/ToolBagTests.cs
git commit -m "說明做了什麼、為什麼、測試數"
```

commit 訊息寫三件事：**做了什麼、為什麼（誰要的或根因）、測試數**。可以參考 `git log` 裡過去的寫法。

### 4-3 自己確認後 push

```bash
git push origin main
```

詳細步驟和遇到錯誤怎麼辦，見專案對話裡「自己推上 GitHub 的方法」。

## 5. 練習題（由易到難）

每題都附「答案在哪裡」，先自己做，卡住再看。

**練習 1（只改資料）**：把工具袋放下的最遠距離從 1.2 m 改成 1.0 m。
- 提示：不用改程式。
- 答案：`Modules/XR/Resources/PostureDef.asset` 的 `toolBagMaxReach`。改完跑 EditMode，`ToolBag_LeftHandDrop_ClampedToReach` 仍會過，因為測試讀的是預設值。

**練習 2（讀紀錄）**：找出你最近一場訓練中，第一次犯錯是哪一步、什麼錯誤、幾秒。
- 提示：`Recordings/<最新>/session.jsonl` 搜 `ErrorDetected`。

**練習 3（純函式＋測試）**：工具袋放下時，讓朝向轉正面向站點（現在是保持放開時的方向）。
- 步驟：
  1. 寫一個純函式，算「從袋子看向站點」的水平角度。
  2. 寫測試：站點在袋子正北方時，角度應該是多少。
  3. 在 `Dropped` 裡套用。
- 參考：`XrPanels` 的 `PanelLogic.FaceHead` 做的是類似的事。
- 注意：這是新行為，做之前先問自己 1-1 的七個問題，並跟團隊確認要不要。

**練習 4（修 bug 流程）**：看訓練紀錄的重播時，工具袋不會回到學員放的位置。
- 提示 1：紀錄裡已經有 `PanelMoved`（`panelId` 是 `toolbag`）。
- 提示 2：重播時 `ReplayPlayer` 會寫黑板鍵 `xr.panel.replay.toolbag`，但沒有人讀。
- 參考：`XrPanels.ApplyReplay` 怎麼讀面板的位置。
- 先寫一句話根因，再動手。

**練習 5（模型）**：在工具袋模型的右側 D 環位置加一個空節點 `Hang_Point_Bag`。重跑 Blender 腳本、匯入 Unity、確認節點出現在場景裡。
- 提示：`gen_tool_pouch.py` 的 `pouch()`，看 `Ring_Tab` 附近，用 `empty(...)`。

## 6. 卡住時怎麼查

| 狀況 | 先看哪裡 |
|---|---|
| 不知道某個功能在哪 | 搜黑板鍵或物件 ID；`Docs/專案設計報告_程式.md` 第 3 節（各模組做什麼） |
| 頭盔裡行為怪 | 最新一場 `session.jsonl`：看事件和狀態的時間順序 |
| 編譯錯誤 | Unity Console 第一條紅字（後面的常是連鎖錯誤） |
| 測試失敗 | 看失敗訊息的中文說明，回頭檢查設計漏了哪個情況 |
| VR 連不上 | Editor.log 搜 `XR_SESSION_STATE`；Link 服務日誌 `%LOCALAPPDATA%\Oculus\Service_*.txt` |
| 場景物件不見、位置錯 | 改的是不是場景？要改 `RoofSiteBuilder` 再重建 |

最後一條建議：**一次只改一件事，改完就跑測試**。改三件事才跑，測試失敗時你不會知道是哪一件。
